# 传FY 与 宣教 重设计方案（v1 草案）

> 2026-07-14 · 基于代码审查 + holiness.uk 线上实测（John 测试账号）

## 0. 现状诊断

**登录链路（已修复，待部署）**
- 前端所有宣教 API 曾发送假凭证 `Authorization: Bearer cookie-session`；cookie 一旦缺失（跨域部署、代理、过期），后端拿假 token 查会话必然 401「请先登录」。已改为：登录响应返回真 token（仅内存持有）+ 请求显式携带 cookie + 不再发送假 Bearer。
- 线上实测：cookie 登录本身可用（/auth/me 200）；`/api/mission-bridge/*` 实际被功能开关拦截，返回 503「Mission OS 当前未启用」（已用迁移 0210 + `MISSION_OS_ENABLED=1` 修复，待部署）。
- HF Space 有冷启动/休眠问题，休眠期间所有 API 503，前端应有统一的「服务唤醒中」提示（见 Phase 3）。

**结构问题（本方案要解决的核心）**
- 邻舍之桥一级标签多达 19 个（项目/旅程/组织/带领者/注意力30天/AI信仰探索/司机同行/夜班同行/流动家庭/专项支持/资料/AI辅助/安全/隐私/发现/设计/导师/运营/事件），把「平台运营者」的企业级功能直接暴露给普通信徒。
- 工作台是 13 阶段的机构差派生命周期（禾场情报→呼召辨识→…→Deployment Gate），术语（禾场/差派/P0-P4/Gate/quorum）是差会运营语言，普通弟兄姊妹无法理解，也没有使用场景。
- 传FY 只有一面「祷告墙」：能发祷告、阿们、导出，但没有对象、没有跟进、没有结果——缺少核心闭环。
- 后端功能真实存在（Postgres 持久化、权限、审计都齐），但被 功能开关 → 租户权限 → 组织上下文 层层拦住，且大量模块从未有清晰入口，形同空转。
- 界面：宣教部分大量内联样式、桌面优先、无空状态引导，移动端体验差。

## 1. 设计原则

1. **一条主线闭环优先**：先让 1 个核心流程完整可用，再谈功能广度。
2. **渐进披露**：普通信徒 / 同工 / 机构管理员看到完全不同的界面；角色由后端 membership 决定。
3. **生活化中文**：UI 层全部去术语化（API/代码不改名）。
4. **安全边界不动摇**：保留现有 safeguarding 设计——自愿参与、随时退出、高风险真人接管、安全求助永远可见。

## 2. 用户分层

| 角色 | 占比 | 该看到什么 |
|---|---|---|
| 普通信徒 | ~99% | 为身边人祷告、参与项目、我的旅程、安全求助 |
| 小组带领者/同工 | ~1% | + 带领者工作台、导师小组、可信资料库 |
| 教会/差会管理员 | 极少数 | + Mission OS 工作台、运营后台、事件处理、群体发现/项目设计 |

## 3. 传FY 重设计：从「墙」到「闭环」

**核心闭环**：挂念名单 → 每日代祷 → 行动建议 → 阶段变化 → 见证 → 慕道班

页面结构（传FY 子标签内部）：
1. **我的挂念**（新，默认首屏）
   - 添加我挂念的朋友（仅填称呼/昵称，隐私最小化，明确提示不要填全名、联系方式）
   - 每人一个属灵阶段：未信 → 留心 → 慕道 → 决志 → 受洗 → 同行
   - 今日代祷卡片：今天为谁祷告，一键「已祷告 🙏」；可选行动建议（发一句问候 / 约一次饭 / 送一本书 / 邀请参加聚会）
   - 连续代祷天数（温和展示，不做羞耻驱动）
2. **祷告墙**（现有功能保留：提交/匿名/阿们/编辑/删除/导出/语音）
   - 阶段推进时鼓励写一段见证，可实名/匿名发到墙上（打「见证」标签）
3. **慕道班衔接**：朋友进入「慕道」阶段时，推荐现有慕道班课程并支持转发

数据模型（新迁移）：
- `evangelism_contacts(id, owner_email, display_name, stage, notes, created_at, updated_at)`
- `evangelism_prayer_logs(id, contact_id, owner_email, prayed_on date, UNIQUE(contact_id, prayed_on))`
- 见证复用 `evangelism_prayers` 表 + `kind='testimony'` 列

API：`/api/evangelism/contacts` CRUD、`POST /contacts/{id}/pray`、`POST /contacts/{id}/stage`

## 4. 宣教重设计：渐进披露

**普通信徒默认只看到 4 个入口：**
- 🌱 项目参与（现有 3 个 program 卡片 + 自愿同意）
- 🧭 我的旅程（目标/签到/暂停/退出）
- 📖 可信资料（只读）
- 🆘 安全求助（任何角色永远可见）

**同工解锁**：带领者工作台、导师小组、资料管理。
**管理员解锁**：Mission OS 工作台（组织/禾场/差派/财务/Gate）、运营后台、事件处理、群体发现、项目设计、AI 辅助审核。

实现：
- 后端新增 `GET /api/mission-bridge/capabilities`：读 `mission_bridge_tenant_memberships` / `organization_memberships`，返回 `{ role, tabs: [...] }`
- 前端 MissionBridgePanel 按 capabilities 渲染标签，替换现在「proposals 能不能读到」来猜权限的做法
- 长尾专项（司机同行/夜班同行/流动家庭/注意力30天/AI信仰探索…）折叠进一个「专项支持」目录页，按需进入，不占一级标签
- 术语表（仅 UI 文案）：禾场→服事群体；差派→差遣申请；Deployment Gate→出发前检查；readiness→预备程度；P0-P4→保密等级
- 路线图从一级标签移到页脚「开发者/关于」入口

## 5. 界面翻新

- 宣教部分逐步去内联 style，统一进 missionBridge.css / styles.css 设计令牌
- 移动优先：一级入口 ≤4 个，横向 segmented 控件；表单单列
- 每个面板给空状态引导（「第一步做什么」+ 一个主按钮）
- 后端 503/冷启动统一提示「服务唤醒中，约需 1-2 分钟」并自动重试

## 6. 分期计划

| 期 | 内容 | 验收 |
|---|---|---|
| **Phase 0（立即）** | push 两仓库、HF/Vercel 部署、线上回归 | 登录后邻舍之桥/工作台不再 401/503；传FY 匿名可用 |
| **Phase 1（传FY 闭环）** | 挂念名单 + 代祷打卡 + 阶段 + 见证（迁移/API/前端/测试） | 新用户 3 分钟内完成：添加朋友→祷告→看到连续天数 |
| **Phase 2（宣教渐进披露）** | capabilities API + 按角色渲染 + 术语中文化 + 专项支持目录 | 普通用户只见 4 入口；管理员可达全部功能 |
| **Phase 3（打磨）** | 视觉统一、移动端、空状态、冷启动提示 | 移动端可用性走查通过 |
| **Phase 4（可选）** | 长尾模块评估：留 / 并 / 砍 | 每个保留模块有真实使用路径 |

## 7. 已确认的产品决定（2026-07-14）

1. 「我的挂念」上限：**20 人**。
2. 见证 **需要审核** 后才公开上墙（当前由平台管理员审核；后续可下放同工）。
3. **教会 owner/admin 自动获得宣教管理员能力**（capabilities API 实现）。
4. 长尾专项模块 **有真实用户，保留**，折叠进「专项支持」目录按需进入。
